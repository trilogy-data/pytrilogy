## The problem

Every statement has a **row universe**: the kinds of row it can return, and which entities exist on each kind. Take customers and orders, where not every customer has an order. `select customer_id, status` has two kinds of row: one with a customer AND an order, and one with a customer and no order.

Before this project nothing in discovery computed that. About a dozen sites each re-derived the fragment they needed from stamps (`Modifier.PARTIAL`, `partial_concepts`, `nullable_concepts`) and from the shape of whatever was already built. They disagreed at the edges, and every disagreement was a wrong answer or a lost filter. The derived-concept key-domain rule (a derived concept is NULL where its key's entity is absent) had no single place to live. The prototype needed five new predicates and three `keep=` parameters, each restating "which rows, which entities" locally.

## The idea

A **keyspace** is computed once per plan, before grouping, from the requested keys.

- A **region** is one kind of row: a set of entity keys that are PRESENT on it. Customers/orders gives `{customer, order}` and `{customer}`.
- The statement's universe is a set of regions. They are disjoint by construction (the Venn diagram's cells, not its circles).
- A concept is **defined** on a region when every one of its FD-minimal keys is present there. Elsewhere it is ABSENT. That renders as NULL, but it is not a NULL value.
- An aggregate is evaluated OVER regions, which is why `count(order_id) by customer_id` is 0, not NULL, on `{customer}`. A row-stream derivation is evaluated ON the regions where it is defined.

Shapes it has to get right (pinned in `tests/core/processing/test_keyspace.py`):

| model fact | regions |
|---|---|
| `orders.customer_id: ~customer_id`, customer key demanded | `{customer, order}`, `{customer}` |
| same, customer key NOT demanded (join axis only) | `{order}` |
| items bind `~user_id` and `~product_id` | `{item, order, user, product}`, `{user}`, `{product}`. No `{user, product}` cell: "families never cross-pair" is this, stated once |
| `returns` binds `~order_id, ~item_id` as its OWN grain, `lines` binds both complete | one region `{order, item}`. `_ret_order` is a NULL VALUE there and `is_returned` evaluates to false (tpc_ds q94) |
| `orders.customer_id: ?customer_id` | one region; the NULL key is a value on a real row |
| `by rollup (k)` | subtotal rows are a grouping product, not a region |
| WHERE null-rejects a concept absent on a region | that region is empty for this statement |

"The span does not FD-determine it" is NOT the region test; that breaks q94. Presence is not FD.

## Owner decisions

- **Regions are keyed by entity keys**, not concepts. A property is never a witness (tpc_ds q70), except where it identifies a source (see regions below).
- **`complete where` stays with the union machinery**; it is not a region fact. It is a trusted containment contract.
- **The keyspace lives on `BuildInfo`, per plan.** `DomainGraph` stays model-level.
- **An aggregate ARGUMENT demands its key's region** (answer 4): `select status, count(customer_id)` counts the orderless customer under `status = NULL`, as the materialized twin does.
- **A filter concept is a value** (answer 5, "a bug, not a choice"): `filter X where COND` narrows only the concept it defines, never the other columns' rows. The materialized twin restricting the stream is the same bug, so the oracle cannot judge it; it has its own expected-rows tests, and it reaches outside `~` models.
- **Two `~` bindings on a key have no defined relationship.** The full set is always a complete source (or a `complete where` slice the union machinery stacks), and that is what a heal completes against. With no complete source the key is not in play and nothing heals: `UnresolvableQueryException: no complete sources`.
- **thelook q22 was rebaselined at 872.** The solid stream as its own CTE beside the user domain is the design's shape.
- **`array_agg` collects present values** (ruled 2026-09-27). A NULL value on a real row is not an element, and a group of only NULLs is NULL like an empty group, as `count(x)` already ignores NULL values. Backends disagree natively (DuckDB and Postgres keep the NULL, ClickHouse's `groupArray` drops it, BigQuery raises), so each dialect lowers to its own NULL-ignoring form: `FILTER (WHERE x IS NOT NULL)` in the base map (DuckDB, Postgres, Presto, Trino), `IGNORE NULLS` on BigQuery, plain `array_agg` on Snowflake (native), `groupArray` unchanged on ClickHouse. The grain-match singleton is `CASE WHEN x IS NOT NULL THEN [x] ELSE NULL END`. `tests/dialect/test_array_agg_null_semantics.py`. Together with the region rule (aggregates over a region below), `array_agg` never yields a phantom `[NULL]`.

## Where it sits

`concept_strategies_v4._build_from_graph` is a three-stage pipeline: `build_concept_graph` -> keyspace -> `build_group_graph` -> `build_strategy_node`. The keyspace is attached to `BuildInfo.keyspace` and handed to grouping, strategy building and FINAL assembly. `_build_from_graph` recurses (rowset bodies, WHERE-phase sub-plans), so a keyspace is per PLAN. Its demand is still the STATEMENT's: only mandatory concepts in `environment.statement_output_addresses` count, because a condition feeder lists its grain keys as outputs, and those are the axis it joins back on (TPC-H q20).

`statement_keyspace` is the one seam every plan's keyspace is built through (population, statement-output filter, witnesses). `partial_bridging.scope_statement` is the one seam for heal: authored and output addresses, `heal_pinned_partials`, `drop_excluded_partials`. Both `get_query_node` and `build_nested_select` call it, because the latter materializes a fresh environment for every rowset body, union arm and merge arm.

The keyspace does NOT own join rendering, source search, aggregate argument inlining or the optimizer; those consume its answers. Aggregate argument inlining is a stage-3 choice: an aggregate re-derives its BASIC arguments from the root, which is why padding must never happen inside one.

**The source search reads no span.** The network search reads `datasource.partial_concepts` once, as one `BindingStrength.FULL | PARTIAL` bit per binding; that bit is also the whole Rust FFI surface for partiality. `non_partial_for` + `condition_implies` can promote a binding per request. `network_coalescing.downgrade_axis_bindings` MINTS partiality for coalescing axes with no stamp behind it. Spans reach source planning only ambiently, through the `MergeNode` environment capture. The legacy single-scan path (`select_helpers/source_scoring.py`, `select_node_v2.scan_stamps`, the only `NULLABLE` reader) has the stronger partiality reasoning.

## Rules as built

Each bullet gives a rule and the shape that forced it. Tests named are the guards.

### Regions (`v4_helper/keyspace.py` builds `core/models/keyspace.py`'s `Region` / `Keyspace`)

The keyspace is a model-level value so `SpanScope` can carry it whole (span scope below). Every span fact a consumer reads is a property or method of `Keyspace`/`Region`, never a second copy: `Region.completes` and `live_completes` are read off `completions`, `Region.has_own_rows` is a bool, `Region.reach` is what the region's spans reach together, `Keyspace.families` is the live regions' span-sets. `_SourceFacts.carried` is stamped per source; `_ModelFacts.reach_of(keys)` is the one lookup, cached per key-set.

- **Entities.** A KEY is its own entity; its `keys` are an FK-path artifact. Anything else resolves through its keys recursively: an aggregate's keys are its `by`, which can be a property or a ROLLUP marker, and a ROLLUP aggregate declares no keys, so `_entity_keys` reads its `by`. A key computed row by row is a function of its arguments' entity (gcat `orbit_code`). A property that identifies some source's rows IS an entity (`region_dim` grain `(region)`).
- **Regions are generated by sources.** A datasource row carries the keys it binds plus what a keyed lookup reaches from them (whole grain only, never through a source whose own grain is bound `~`). Each carried key remembers the `~` bindings on its path (its cause). A source carrying a proper subset of the entities witnesses a smaller region. That region survives only when every source carrying MORE reaches its identifying keys through a `~`; those keys are the region's `spans`. An entity no source relates to a region's rows is cross-joined onto them, so it is present there. Model components (sources sharing a column), not single rows, decide that.
- **Sources without a declared grain** are identified by every KEY column they bind, less those the others determine by FD (`minimize_build_grain`). The earlier rule dropped a key that identified another source on its own, as a foreign key; that is right for `customers (id, nation.id)` and wrong for `lines (order_id, line_no, product_id)`, where `order_id` and `product_id` each identify a source and `line_no` alone is not a line: read as one row per `line_no`, a return keyed on its line joined every order's line of that number (`select return_id, reason, qty` gave return 901 three lines; `tests/engine/test_grainless_source_identity.py`, a declared-vs-undeclared grain twin). Not all FKs can be told from grain members, so none is dropped without an FD. The cost: an ungrained `customers (id, nation.id)` is one row per (customer, nation), and no lookup from an order enters it; TPC-H instantiated leaves its `grain (id)` commented out and plans without the nation extension. Declaring the grain is what makes the FK one.
- **Fan-out bridges.** When no lookup leads from A to B (a launch has many engines), no single source carries both, and the partial source joining the region to the rest keeps the unmatched members a region (gcat `test_should_group`).
- **Generated keys** (`unnest`, constants) are the complete side of a `~` merged onto them. <- owner note; this is not a specific fact of them, all merges that declare the right authoritative have this behavior.
- **A `~` survives a merge** and is found through `origin_concept_address`. Facts are read whether or not a license survives heal; otherwise one entity is spelled `c2` in one plan and `customer_id` in the next.
- **Demand** is the election's question: a span is demanded when some output is a function of what a lookup from the span ALONE reaches (`Keyspace.span_reach`, `output_demanded_spans`). TPC-H q20/q9 and TPC-DS q05 separate this from "any output defined on the region". **A composite-key region is demanded by what its spans reach TOGETHER** (`Region.reach`, `_ModelFacts.reach_of` over the whole span-set): `grain (vname, variant)` is entered only with its whole grain, so `vclass` is reached by neither span alone, and `select vclass, status` evaluated the CASE's ELSE on the unlaunched vehicle (gcat's composite `~`, once "never marked demanded"). `carried_on` reads the same joint reach.
- **Completions** (`Region.completes`, `Region.completions`): a source the plan NEEDS that holds only some of a region's rows beside a source holding all of them (`returns` beside `lines`, a partial aggregate table beside its dimension). "Needed" matters: TPC-DS `store_returns` binds `~item.sk, ~ticket_number` model-wide, and only a statement reading a returns measure is completed by it. `Region.live_completes`: an emptied completion demands nothing.
- **`emptied_by`**: a WHERE null-rejecting a concept that is absent on a region empties it. This follows the RULE, so derived concepts count. It uses `gather_non_null_proofs` (BETWEEN included; `condition_proves_non_null` alone missed it: TPC-DS q77). The filter population (`statement_filter_population`) feeds it too.
- **`in_play_spans`**: every region's `spans | completes`, emptied regions INCLUDED. Their rows are gone once the WHERE runs, but a merge below that point still sees their padding.
- **`Region.witnesses`** (whose rows a region is) and **`Region.has_own_rows`** (some complete source witnesses it). A region kept only as a completion has no row where an entity is absent, so it gets no domain. Found through a `persist` into the session environment (`test_website_demo` fan-out).
- **Queries**: `Keyspace.defined_on(address, region)` is what absence means. `Keyspace.carried_on` is what an extension row holds, keyed on what a lookup from the region's spans reaches TOGETHER (`Region.reach`; a cross-joined entity is present but not carried, and an empty reach is the composite answer, never a fallback to the per-span union). `keys_by_address`, `entity_keys`, `binding_is_complete(source, span)`.
- **A BASIC is keyed on what it READS**, not on its declared keys (`keyspace._read_addresses`). `coalesce(sum(amount), 0)` lists `order_id` as a key, and treating it as absent gave the ROLLUP trap a domain. <- owner note; this is interesting; like an aggregate the input rows are probably determined by their keyspace, yes - does that make basic *less* unique?
- **An existence-only node** is a semijoin's subselect, not a row of the plan. Spans are named by the address bound `~`, entities by the canonical spelling.
- **A rowset key is its own entity**, not the key it wraps: `select even_orders.store_id` must not gain stores no order references. `select s.sk, item_desc` is disconnected, and the keyless guard rejects it.

### Region domains (phase 4; `v4_helper/region_domains.py`, `group_graph`)

A live, demanded region with own rows gets a ROOT bucket of its own, the region's **domain** (id `grp:root:root:∅:extent:<spans>`, `GroupAttrs.extent_spans`). Every demanded region with rows of its own has a domain, and `region_domains.DomainKind` says where its rows come from: a bucket of its own (`OWN`, the case described here), the scope's row stream when it sources nothing absent on the region (`ROW_STREAM`), an unsplit rowset boundary (`BOUNDARY`), an authored coalescing relation that already unions its spans (`RELATION`: `union join ocust = cid` IS that key's domain), or the padded plan standing in (`PADDED`: a materialized rollup, a WHERE atom no host can apply to the domain).

```
grp:root:root:∅                          (customer_id, delivery_date)  solid: orders rows only
grp:basic:d*:…                           (status)                      over the solid stream
grp:root:root:∅:extent:local.customer_id (customer_id[, name])         the region's rows: customers
FINAL                                    customers LEFT JOIN status-stream ON customer_id
```

- **Demanded** (`_region_is_demanded`): an output is a function of what the span reaches, or an aggregate counts the region's rows. Otherwise FINAL adds all-NULL rows past the WHERE (gcat `test_merge_with_filter`).
- **The spans ride hidden** as a secondary member of the domain and of every bucket it was split from (`region_join_keys` in `_compute_concept_sets`, ROWSET buckets included), and they are the join axis everywhere. `_final_merge_grain` counts `extent_spans`. `_refresh_input_contracts` puts them in every parent's `preserve_keys`, so no domain is sliced below its spans. `_project_basic_aggregate_inputs` keeps them. FINAL emits the spans its parents READ.
- **Only a bucket that MIXES pads.** A bucket holding only one kind is solid, or the dimension. Reading otherwise made an order-keyed dim peel "the region's rows", or fanned orders out by the other family's span.
- **A domain contributes ROWS** (`_add_region_domain_contributors` adds it as a contributor of no concepts), and it stays whole at FINAL (not bucketed per natural grain by `_wrap_for_grain`). It is added after `_promote_final_aliases_to_grouping_contributors`, which deletes contributors left with no concepts.
- **What the domain carries is PARTIAL on the solid stream**, like the span key (`_extent_free_partials`, `SpanScope.extent_free_carried`). Without that, an aggregate `by name` makes the domain look redundant and drops it.
- **The solid stream reads a span from the fact's own column.** A group built not to extend a span has that span promoted to a full binding in the network search (`network_build._candidate`) and in the legacy renderer (`excluding=`); `_complete_partial_requested` skips it. A group that reads no domain does not EMIT a carried member to a consumer that does.
- **Every row-stream derivation the region carries reads the domain** (`feed_region_domains_to_present_scalars`). A derivation that reads something carried reads the domain of every region it is NULL on the padding of (`null_on_padding`, in `extent_ownership.py`). Without "reads something carried", q77's trivial rename padded for nothing; without "every region", q08 stitched a FULL. When such a group READS only carried things (`_reads_only_carried`), the ROOT lineage edge is dropped, so it is not evaluated on the padded solid stream (the `upper(name)` fan-out).
- **Carried-only members sharing a bucket with something absent** get a bucket of their own (`split_carried_only_row_streams`, `:reads:<span>`). A rename beside a `grain()` hash in one `sig:` bucket lost its label otherwise.
- **The domain takes a member of the region any other ROOT peel holds** (`add_region_domain_buckets`, `holders`): `brand` under `dim:item_id` beside a product domain carrying only `cost` (the peel is keyed on the item, so it neither mixes nor is keyed by the region). Left there alone, only the peel's unpromoted completion at FINAL put the member on the extension row. The cover then reads such a member off the domain or off a group that read the domain (`_cover_groups_for_mandatory`'s owner rule: the `pair_cost` BASIC, and `_fold_descendant_contributors` routes the user domain's `state` through it too). Not a materialized aggregate (`_holds_a_materialized_aggregate`, the rollup that gets no domain, below), and never into a ROWSET domain.
- **A solid ROOT's FINAL re-source runs under its group's own scope; a domain's keeps the FINAL's** (`_assemble_final_node`, `_fresh_final_root_projection`). At FINAL scope, unpromoted, a solid root beside a region domain completed its `~` keys itself: the optional-entity twin's `select order_id, item_id, qty, return_id, reason_label` (materialized) rendered `lines FULL JOIN (lines LEFT JOIN returns)`, and is `lines LEFT JOIN returns` now, the derived spelling's shape (`test_optional_entity_solid_stream_reads_returns_alone`). A domain is the FINAL's own rows: the customer domain completes its transitive `~` address at FINAL scope, and the orphan address's `state` is read off it (`test_licensed_transitive_attr_span`); under its own scope that completion went INNER and the orphan lost its state. Cost: a FINAL dedup over the domain merge reappears on `test_keys_only`/`test_join_grain` (+30 chars), and the forked full column set routes `state` through the BASIC (+80).
- **A rename of what the domain carries is rendered on the domain** (`_add_region_domain_contributors`). An alias rides its source's ROOT bucket, so the feed rule never sees it. When a contributor groups by the rename's source and the solid row stream carries only the hidden span, `_bridge_unpaired_parents` bridges them through the domain; the join order below is what keeps a `~?` guest (no domain row) reaching the aggregate's NULL group.
- **`solid_groups` seeds** are derivations that TAKE A VALUE on the padding (`takes_a_value_on_padding`), plus row streams that must not see an extension row.
- **A MATERIALIZED aggregate beside a region gets no domain of its own** (thelook `sales_agg`, a rollup over the region's rows held as a ROOT; `_holds_a_materialized_aggregate`). Such a bucket seeds no domain and keeps the padded plan; it is rows-right that way (the rollup-summary twin in `tests/engine/test_unmodelled_regions.py`, with the zero-fill of a rolled-up COUNT and the read-as-built domain parent under aggregates below). A mandatory output no contributor renders raises, rather than FINAL silently projecting what it had.
- **The OPTIONAL entity is modelled.** `returns` binding `~order_id, ~item_id` plus its own `return_id` is a larger source reached through a `~`, so `{order, item}` is a region with those spans (`test_optional_entity_is_absent_on_rows_without_it`).
- **An undemanded region is never extended** (`region_domains.undemanded_spans` -> `SpanScope.unextended`, read at ONE site: `MergeNode`'s `demanded_domains`, which licensed an extension per VISIBLE column, `name`'s key under `label`, where the keyspace's demand is per statement). Riding `owned`/`extent_free` instead was tried first and reverted: those also promote the fact's `~` binding to full in the network search and drive the in-play FULL typing of the two-fact regions the keyspace does not model, so TPC-DS q83 grew 7% (per-arm date joins) and `_q83_sales_returns_full_join` lost the FULL the MySQL lowering fixture exists for. A live region with rows of its own that no output reaches and no aggregate counts is not a row of the statement, and before this the network search still completed its `~` with the dimension, customers-preserving: `select order_id, label` returned a fourth row `(NULL, 'cat-in-transit')` (CONCAT is null-opaque, and `label` reads `name`), and `select status[, sum(amount)] where count(order_id) by customer_id = 0` evaluated the CASE on the padding (`'in-transit'`). Both are `[]`/three rows now, as the plain model says. A WHERE over an aggregate BY the span does not demand the region by itself (the rule is outputs and aggregate arguments); `select status, count(customer_id) ... where count(order_id) by customer_id = 0` still returns `(NULL, 1)` because `count(customer_id)` does. Coalescing spans are left to the union machinery, as for domains.

### Aggregates over a region

- **A scalar aggregate `by *` over a `~` region is rows-correct as planned** (TPC-H q22, once listed here as "keeps its padded plan"): `avg(bal) by *` under `then where ... and order_id is null` is evaluated over its argument's key rows, each customer once whatever stage 1 rejected on the order side, and the LEFT JOIN + `is null` plan is the anti-join. Eight spellings against reference SQL in `tests/engine/test_scalar_aggregate_over_region.py`. The emitter fires on q22 and on three of those spellings in a full-suite sweep, and not in a tpc_h-only run (the order dependence under Process): the padded plan is the verified one.

- **An aggregate is evaluated OVER the region** when a grouping key is carried (`count(order_id) by customer_id` is 0; `coalesce(sum(amount), 0) by rollup (customer_id)` is 0 on the orderless customer and 60 on the grand total) or when its argument is (`count(customer_id) by status`, `_aggregates_over_region`). The domain is then not a FINAL contributor a second time.
- **Its named BASIC arguments are computed on the solid rows FIRST** (`_project_basic_aggregate_inputs`), then the domain merges in: `count(status)` must not count a padded row. The seam classifies parents by `region_reads`, the solid side being the complement, **except a condition feeder keyed by the span** (a CONSTRAINT parent whose grain is within the domain's spans: `count(return_id) by item_sk = 0` under `count(sale_id) by item_desc`), which joins the UNITED rows after the domain. Merged onto the solid stream it lost the member the solid stream lacks: an item with a return and no sale was padded past it and read its count as 0 (`test_unmodelled_regions` two-facts cases). On one fact that merge lost nothing, which is why open item 3's prediction looked wrong there.
- **A region domain is read as built by its grouping consumer** (`_parent_nodes_for`, `parent_for_consumer`). A ROOT parent of an aggregate is otherwise re-sourced as a slice of the columns the consumer needs whenever the slice strictly prunes the leaf set, and that fresh scan holds no region (`region_spans` is stamped when the domain is built). Unstamped, the domain parent counted as a SOLID parent at the aggregate, and `count(status)` was evaluated over the padded merge: the rollup-summary twin's `select customer_id, total_amount, order_count, count(status) as s` gave the customer with no order 1. It had been rows-right by accident: the slice hit a stale scan cache (next section) and got the summary table instead of the dimension.
- **An INLINE argument that takes a value on padding** (`sum(case when undelivered then 1 else 0 end)`, `count(grain(...))`: the hash coalesces NULLs) keeps the aggregate solid, and the domain pads at FINAL. Never over the region when a row stream that must not see an extension row reads it (`order_status <- case when qty = min(qty) by user_id ...`).
- **A NULL-collecting aggregate over an absent argument is solid too** (`enums.NULL_COLLECTING_AGGREGATES`, read at the same seam as the inline rule, `_argument_takes_a_value_on_padding`). Evaluating OVER the region is right for every operator whose padded-row answer equals its empty-group answer (`count`/`count_distinct` 0 both ways, the rest NULL both ways); `array_agg` is the one disagreement, `[NULL]` where no rows at all is NULL. So `select customer_id, array_agg(amount)` collects on the solid rows and the domain pads the orderless customer NULL, while `array_agg(customer_id) by status` (a carried argument) still collects her under the NULL status: the padded row's key is a real value (`ARRAY_AGG_CASES` in `test_derived_key_domain.py`, hand rows on both twins since the materialized twin pads the same way).
- **A COUNT the domain pads is 0, said by the merge that pads it**: `QueryDatasource.zero_filled` -> `CTE.zero_filled`, coalesced by the dialect. The older "nullable COUNT through a join" guess stays for materialized aggregates. A union-join arm's absent count is NOT 0. **`CTE.zero_fills_count` is the one seam** for "this CTE renders this count as 0". It reads `enums.ZERO_ON_EMPTY_AGGREGATES` (COUNT and COUNT_DISTINCT: the only aggregates whose empty-group value is a non-NULL constant, so the only ones a padding join can leave wrong -- every other aggregate is NULL both ways), and the multiselect-arm veto is tested BEFORE a stamped `zero_filled`, which `MergeNode._zero_filled_counts` cannot apply since it stamps from the merge's regions alone. Its readers: the dialect (a rolled-up COUNT too: a sparse summary's `order_count` summed through a GROUP BY under `name` was NULL for the customer it lacks), `MergeNode._join_proofs`, the optimizer's `UpgradeJoinOnGuards`, `_push_having_into_group_parent` and the scalar pushdown's null-extension gate (`_predicate_safe_past_null_extension`) all read it. A predicate over such a count (`count(order_id) by customer_id = 0`) ACCEPTS the padded row, so it proves nothing about the side that padded it, is not a HAVING of the aggregate's own group, and does not cross the join that pads it: the condition object is `count = 0` (the `coalesce` is the dialect's), so `condition_proves_non_null` alone read it as null-rejecting and pushed it through the domain's LEFT into the solid side, from where the HAVING relocation followed (`select status, count(customer_id) as n where count(order_id) by customer_id = 0` gave every customer under the NULL status). The merge stamps the WHERE's own inputs, not only outputs (`_zero_filled_counts`).

### The region contract on nodes and join typing

- **`nodes.base_node.region_reads(node)`**: the spans whose extension rows are rows of a node's stream. It stops at a rowset boundary (`StrategyNode.region_boundary`). Two contributors stand in for each other's columns only when they read the same regions; the three folds and `_parent_nodes_for` check it.
- **`StrategyNode.region_spans`** is set when the domain is built (it survives `copy()`; `_elide_single_parent_passthrough` must keep it). `StrategyNode.resolve` stamps `QueryDatasource.region_spans`, and `QueryDatasource.__add__` must carry every span field. `region_spans` and `zero_filled` union; `extent_free_spans` takes the LHS (the key the merge folded the other side under) and `extent_free_carried` follows it, since a union there would claim an address carried by a span the merged source no longer routes -- the other side's own tree keeps its marks for `deep_extent_free_carried`.
- **`get_join_type` reads it per pair** (`region_holders`). The side holding the region joined on its span is preserved. The feeder is preserved too where its key holds a value NULL (`extent_nullables`, chained through lookups keyed on a padded column). The join is FULL when the merge holds a second family, counted over `SpanScope.regions` (the plan's live region span-sets) rather than the spans held: a holder unions the spans of every region it reads, so counting spans read one composite-key region as two and forced FULL on 12 holder/feeder joins across the planner suites. Two holders of one region pair plainly. Every merge with a domain parent is a `host_stitch`. `_is_filter_population` never calls a side the population against a partner holding the region.
- **Value NULLs** (`_unpaired_value_nulls`, holder and host vetoes alike). On the region's own key an EXTENT null on the feeder always vetoes: a guest names no member. A VALUE null, there or on any other key, pairs null-safely with a value NULL the holder carries, so a nullable stand-in key joins LEFT.
- **Guest padding is a NULL no holder row is** (`guest_padded_addresses`: `extent_null_addresses` without the `?` leaves, i.e. the columns a VALUE-NULL-driven outer join padded, chained). A `~?` guest's description is NULL through its NULL item; the domain's `?` member is not that guest, so the feeder's value NULL is unpaired unless the other side is padded for the same guests, and the merge is FULL (`count(grain(order_number, item_desc))` stays solid, and its guest group has no item row). The optimizer's `_narrow_directionally` has the same test (`_unpaired_guest_padding`): a null-safe pair proves nothing for guest padding, and it narrowed that FULL back to LEFT. The guest set is matched through the merge's canonical map (`c~d` for `item_desc`). `extent_nullables` is NOT: it matches raw addresses against canonical nodes, so an aliased key never counts as extent-null there. Fixing that was tried: it restates TPC-DS q64's pushed atoms at the FINAL (`test_q64_rowset_join_with_second_fact_join_hoist`, +870 chars, rows unchanged) and nothing else moved, so it is left as a latent mismatch.
- **The stitch on the span pivots first** (`resolve_join_order_v2`: a held span sorts ahead of every other key). Pivoting on a key the region CARRIES joined the aggregate by the description to the domain alone, and the guest, whose key is a value NULL, never reached its NULL group (`select item_desc as d, quantity as q, count(order_number) by item_desc as n`). Stitched first, the aggregate joins the united rows null-safely on the domain's column, which is NULL on the guest row. Plan-shape cost, verified by rows: thelook q19 orders its FULL to `products` before the LEFT to the order aggregate.
- **An extent-free span is INNER at plan time** when the other side carries the span's whole domain (`complete_key_domain`: an unfiltered, unlimited complete scan, or a read keeping every row of one through `preserved_sources`) and the binder has no NULL on it. This is the plan-time half of the optimizer's `_pair_side_fully_matches`.
- **The padding-provenance matrix** (`_span_padding_matrix`) reads its own plan's keyspace: `in_play_spans` plus `witnessed` (rowset body spellings, see below). `_span_spellings` names a span through its `scoped_join_key_groups` group, since a scoped join keys the pair on its canonical.
- **The host grain** (`MergeNode`, `host_stitch`) reads its OWN plan's spans, not the tree's. A rowset below is a row source.
- **The FULL narrowing (`grain_utility.downgrade_join_for_proofs`) forces a side by a side-only column only when that column is bound completely and plainly there.** A value the domain carries is PARTIAL on the solid stream (`_extent_free_partials`), so `where item_name != 'B'` over a `~?` model (the merge is FULL: the guest's key is a value NULL) no longer keeps the solid side and drops the unsold item. The key-tuple rule keeps forcing through a `~` key: it is what keeps an undemanded region's rows out (`select order_id, status where customer_id in (1, 3)`, the oracle). TPC-H instantiated `adhoc07` (SQL-only) kept two FULLs at FINAL under this (`lineitem-side FULL order_sales FULL customers`) until the solid root's FINAL re-source ran under its own scope: the customer-keyed solid root no longer completes its `~` there.
- **A partial-driven FULL's spine preserves a later relation only where the spine is demanded** (`ensure_content_preservation`, `demanded_domains`). Two facts partial on `order_id` (`lines` and `returns`, each `~order_id`) are related through the complete `orders` scan: `lines FULL returns` on the line, then `orders` keyed on the FULL's spine. Keyed ON the spine that relation used to be upgraded to FULL unconditionally, and `select return_id, reason, qty` admitted the order with neither line nor return as an all-NULL row. `get_join_type` had typed both `orders` pairs LEFT (fact-to-dim anchoring reads the demand); the upgrade now asks the same question. TPC-DS q83's item IS demanded, so its FULL stands (`_q83_sales_returns_full_join`, `test_partial_key_assembly_shapes`). Found by the grain twin (`tests/engine/test_grainless_source_identity.py`, `UNDEMANDED_PIVOT`); the two-fact region it stands in for is open item 1.
- **A collapsed CTE keeps its partial marks** (`optimizations/utils.carry_child_state`). The optimizer's `_blocked_partials` is what stops a non-null proof on a key from forcing a side that binds it PARTIALLY; the solid pre-merge of an aggregate over the region carries the span partial (`_extent_free_partials`), and `CollapseSingleParent` folded that projection into its GROUP and dropped the mark. The FINAL INNER-joins the aggregate on `s.sk`; that equality flowed back as an external proof on the aggregate's input merge, where `s.sk` renders from the domain, and with nothing blocked it was read as proving the solid side's key, turning the domain's LEFT into INNER (`EQUIVALENT_SPELLINGS`, the multi-aggregate keyed rowset). Scoping the proof to the rendering side instead was tried: it also stopped a proof on a complete dimension's key (TPC-DS q64/q23 dim lookups went LEFT). **A source both sides read is exclusively neither's** (`_downgrade`): `_blocked_partials` tests exclusivity on physical source tokens, and the solid stream of a region reads the domain's dimension scan for an attribute (`tier` under `tier_amount`), so the span rendering from that scan on the domain's side looked bound only by the solid side, and the FINAL's INNER on the span (an address-level `direct` proof) narrowed the domain's LEFT (`select customer_id, name, sum(tier_amount)` lost the orderless customer; `select customer_id, sum(tier_amount)` has no FINAL join and was right). Each side's exclusive set now subtracts the other side's tokens and CTE names.
- **A preserving join is part of a merge's identity** (`QueryDatasource._compute_identifier`, `_null_extended_sides`). The signature names the NULL-EXTENDED side, so `a LEFT JOIN b` and `b RIGHT JOIN a` are one relation. Otherwise two differently-typed merges share a CTE, or two copies of one merge fail to fold.
- **Span scope**: `BuildEnvironment.span_scope: SpanScope` is set and restored as a unit and captured whole by `MergeNode.span_scope`. Plan-level it holds the `keyspace` itself (a merge reads `in_play_spans`, `output_demanded_spans`, `witnessed` and `families` off it), `owned` and `unextended`; group-level `extent_free` and `extent_free_carried`. `output_demanded_spans` are coalesced keys for three narrowings: the merge's own WHERE (`_join_proofs`), a branch's filter over a key it was built not to extend, and the "filtered branch is the population" rule.

### WHERE by region (phase 5; `condition_placement`, `projection`)

- **A value the region's rows carry is deliverable** (`_filters_region_domain`, via `carried_on`). A domain member filters the domain. A carried value no domain column holds (a scalar over an aggregate by the span) has its producer read the domain, the condition phase included (matched on scope, not label). The atom is restated at FINAL over the united rows (`PlacementReason.FINAL_SPAN_DOMAIN`, `_reads_past_region_domain`), and the producer's constraint edges into the solid stream are dropped (`detach_final_span_domain_producers`).
- **A host the domain FEEDS is where the region's rows unite for that atom.** Placement hosts the atom at the domain-fed grouping candidates (`_region_domain_grouping_hosts`), FINAL only when there are none, and the detach keeps the producer's CONSTRAINT edges into the hosts the atom was PLACED at only. Without this, a null-accepting atom over an absent value under an aggregate by the span was applied above the aggregate (13 oracle DIFFs), and an aggregate grouped by an absent value was wrong on both models (the oracle is blind to it; hand-computed rows in `test_atom_under_an_aggregate_the_domain_feeds`).
- **An atom over aggregates BY the span is a per-member value** (`_over_aggregates_by_span`): it is hosted at FINAL rather than on the input of a sibling aggregate keyed by the span (`_grain_within_a_span`): applied there it dropped the member's rows and the domain padded the member back with the count read off the filtered stream (`select item_sk, count(sale_id) as s where count(return_id) by item_sk = 0`). A host grouped by something else (`count(customer_id) by status`) still takes it on its input rows, member by member (open item 3).
- **A condition source joined to a region holder is not forced INNER** (`condition_injection.inject_condition_at_node`): the feeder's missing row IS the aggregate's value there (a zero-filled COUNT, a NULL sum), so join typing decides (LEFT toward the holder) and the WHERE tests it. Forcing INNER dropped the customer with no order from `where count(order_id) by customer_id = 0`.
- **The condition phase's fact scan carries the span** (`carry_spans_to_condition_scans`, after `_add_d1_root_buckets` builds it): a null-accepting WHERE over an absent value beside dimension-only outputs (`select customer_id, name where status is null`) reaches FINAL as a producer of its own, and without the span its merge with the domain was `ON 1=1`. **A sole contributor holding the region takes that atom BEFORE the dedup to the output grain** (`_assemble_final_node`, `region_paired_feeders`, beside the presence-probe and relation-paired cases that already did): `select name where status is null` hid the span from the domain first and tripped the keyless-join guard.
- **Only when the final rows decide the atom** (`projection.decided_at_output_grain`): every output crossing an aggregate is grouped at a grain determining the atom's input, judged only over outputs the domain does NOT feed (`_fed_by_region_domain`).
- **Such a WHERE alone earns the region a domain** (`where_over_region`).
- **An atom over the span key keeps the extension row** (`where customer_id in (2, 3)`).
- **A null-rejecting atom over an absent value empties the region**: no domain, the filter sits on the fact side.
- **`null_padded_nodes` walks the accumulated left** of a RIGHT/FULL join. A null-ACCEPTING atom must not push below it. `_push_having_into_group_parent` reads the same gate (`_predicate_safe_past_null_extension`). It must also stay blocked until the final join upgrade: pushing a null-rejecting HAVING early materializes a retained duplicate (usa_names `test_filter_constant_with_constant`).
- **`_preserved_final_branch` is RETIRED.** It restated a side-branch atom at FINAL against a row-preserving join. Once joins were typed at plan time it fired on 23 planner-suite tests and changed the SQL of two, both redundantly (a WHERE pushed onto the rowset side of a LEFT join whose preserved side carried it; `city = 'USBOS'` over two sources `complete where city = 'USBOS'`); rows identical everywhere. The sweep that once showed it load-bearing on ~20 tests predates 5(a).
- **`_uncovered_exposing_output_contributor` is KEPT** (swept 2026-09-27 the same way: `local_scripts/keyspace_ab/ks_uec.py`, planner suites with the rule on, then answering False). It fires on 15 tests; with it off, 12 plans change and it is load-bearing on six: the region scalar aggregate's `where bal > avg_bal` (the `by *` aggregate under `__preql_internal_all_rows`, a rows test), the three partition row-gates (`test_row_gate_on_partitioned_target_plans_inside_partition_scope`, rows tests), TPC-DS q01's `total_returns > 1.2 * avg` and gcat `test_date_filter`'s `BETWEEN`; each lost its WHERE entirely, not a restatement. Its shape is a global or by-`*` aggregate joined back onto the rows it was computed over: the atom's host is the aggregate's input branch, the unfiltered projection re-enters FINAL, and the FINAL restatement is the only copy that survives. The other six diffs were one redundant restatement (`test_partitioned_sources_prune_to_cluster_anchors`, rows unchanged) and the known noise (four file-source temp paths, `test_environment`).

### A filter concept is a value (owner answer 5)

- **No push in intermediate shapes.** `gen_filter`'s carve-outs are deleted. A filter group's predicate narrows its ROWS only when the statement SHOWS nothing but filter values over that one predicate AND this group produces them (`_filter_intrinsic_pushdown_safe`, on `statement_filter_population`). The push is over the parents as built, never a statement WHERE (`test_filter_mixed_aggregate_row_predicate`).
- **A hidden output is not shown.** `statement_filter_population(mandatory_list, hidden)` reads `BuildEnvironment.statement_hidden_addresses` (set in `scope_statement`), so a HAVING aggregate promoted into the mandatory list does not block the push (TPC-DS q41; it was wrong rows on the plain model too).
- **A responsive aggregate in the HAVING** blocks the push only when the consumer reads something off the unfiltered ancestor that the filter group does not emit (`_consumer_reads`: a group's grain and what rides through it are read as themselves). `select even_name having count(order_id) > 1` returned the NULL group before this.
- **A pushed predicate is not rendered twice.** `dialect/base.py::_filter_guaranteed_by_parents`: the per-row CASE is elided when every source of every column the filter reads is a parent whose WHERE implies the predicate and no join in the CTE can NULL-pad a row (INNER only). The sole-parent form of this rule predates it; the responsive-HAVING shape pushed the predicate into both scans and rendered the CASE over their join.
- **A property collapses to its grain.** The FilterNode groups to the outputs' entity grain (`keyspace.entity_keys`) whenever a predicate input is not FD-determined by that grain (`build_fd_determines`), and `CTE.filter_collapses_to_grain` MAX-collapses it. This does not apply under an aggregate consumer (`count(line_no ? ...)` counts the per-row CASE: TPC-H q4).
- **The population reaches the row universe.** The keyspace (`emptied_by`) and pin-heal both read it; otherwise an emptied region still pads and `delivery_date is null` is TRUE on the pad.

### Pin-heal (`partial_bridging`)

- `Keyspace.binding_is_complete(source, span)`: a source's `~` costs nothing when the WHERE empties every kind of row that source has no match for. Healing P's `~` forgets only the members P lacks, so a live region P itself witnesses does not block it.
- It trusts derived null-rejections (`_proven_bound` stands a derivation for its entity keys).
- Heal is restricted to the statement keyspace's in-play spans (model-wide heals were inert).
- It keeps its own anchor guards (`_pair_anchors` / `_anchors_dispensable`), because healing must be safe for every other merge the dropped `~` licenses. It also keeps the model-component gate on killers and the `then where` exclusion. **A sibling itself `~` on the key is not an anchor** (thelook q16 was a heal artifact of one).
- **It stays a datasource REWRITE at the statement seam, and that is correct.** `generate_graph` captures datasource objects, so a heal after it rewrites a mapping nobody reads; per-plan healing inside `_build_from_graph` gave 17 failures. The heal audit (`local_scripts/keyspace_ab/ks_heal_audit.py`) showed that "one keyspace per plan with the plan's own conditions" is WRONG. A window feeder with no WHERE of its own would pad the orderless customer and `row_number` it. Heal is a STATEMENT fact every sub-plan inherits. So the keyspace is built twice per plan (heal's over authored bindings, the plan's over rewritten ones), by design. Re-run the audit if heal or the keyspace's facts change.
- Not done: pin-heal never heals a MERGED `~` key (`_structural_partial` compares `column.concept.address` only). That is conservative, a lost optimization, not a wrong answer (gcat `payload.launch.launch_tag`). The heal keyspace takes no rowset witnesses; that was probed with no oracle failure.

### A rowset as a witness (`rowset_witness.py`, `keyspace.RowsetWitness`)

- **A rowset the plan reads is a source of its keyspace** (`_rowset_sources`). Its rows are the body's live regions, respelled in the handles: one `_SourceFacts` per body region, grain the key handles present, and a handle bound `~` when a smaller region of the body spells its key as a span. Grain and bound keys go through the reader's canonical map (`_respelled`), so a rowset over a rowset composes. The body keyspace is computed as the body's own plan computes it (`build_nested_select`, healed) and cached per rowset on the history. A multiselect body gets no regions. A rowset in progress is an empty witness: a body cannot witness itself (TPC-DS q64 recursion). Only the frame that OWNS the placeholder caches its result -- anything witnessed while one was live understates it, so mutually recursive bodies would otherwise persist each other's partial answer for the whole build, and a raising `_witness` would leave the placeholder standing as the answer.
- **A key no handle spells is spelled by the handle keyed on it alone** (`s.d` for `item_sk`): that handle is the region's present handle, its span, and its padding's name. With several such handles the one that cannot be NULL comes first (a `string?` stand-in pairs its NULL member with a NULL-keyed guest and vetoes the join into a FULL), then by name. Every other handle keyed on that key LIVES ON the stand-in (`RowsetWitness.entity_handles` are the reader's declared keys in `build_keyspace`): reading `s.n` alone still resolves to the `s.d` region. Before that, the reader saw one region and counted the unsold item's padded hash (`test_stand_in_beside_a_second_property`). If there is no such handle, the region stays out of the reader's plan: probed with a body demanding the region only through an aggregate argument (`count(item_sk) by order_number`), and the reader is right to read the rowset as a row source (the NULL-`o` row is a real row, and a CASE over `s.n_items` evaluates on it, where the direct spelling's CASE over an aggregate by `order_number` is absent there).
- **A body region the reader reads nothing of is not a row of the reader** (`Keyspace.unread_spans`). A witness region none of the plan's requested entities is present on (`select s.o, s.st` over a body naming the customer; the product family under `select s.u, count(s.i)`) has no region in the reader's keyspace at all, so `undemanded_spans` could not name it, and the padded body came up as a row source (`(NULL, 0)` for the product no user bought). Its spans join the undemanded set, and the boundary plans its body OWNED for `extent_free | unextended` (`rowset.py`), as for a span the reader's own domain holds. Matched through the body plan's canonical map (a nested rowset spells `t.c` as `_s_c2`). A region the reader COLLAPSES is different: `select s.c, s.k` over an aggregate body reads only customer-level handles, so the body's two regions are one region of the reader and every body row is its row; "not in play" was tried as the test and dropped the orderless customer there. The no-handle carve-out above is unchanged: that region has no spans. `tests/engine/test_rowset_unread_region.py`.
- **`RowsetWitness.spellings`** maps every spelling a join inside the body pads a span under to the handle -> `Keyspace.witnessed`, read through `SpanScope.keyspace`.
- **A rowset bucket is split for a region only when something must be evaluated on the solid rows** (`_needs_solid_rows`). A plain read of a padded rowset keeps its one boundary, which is already the region holder. The domain is a ROWSET bucket, a `force_group` GroupNode over the boundary, to its members; `_carry_join_keys` never widens a rowset domain (a ROOT domain must still be widened with a key it binds: `test_licensed_transitive_attr_span`).
- **The solid side is the body planned with the region OWNED above** (`SpanScope.owned`, `V4History.owned_spans`, part of the build key; `body_spans_of` maps reader spans to body spans). The body KEEPS its region, since a window or aggregate it computes over the region must still read the domain, but no group extends the span. `resolve_rowset` marks the owned spans' handles and carried handles partial.
- **A handle is NULL on padding like a ROOT column** (`null_on_padding` treats `Derivation.ROWSET` like ROOT).
- **A handle's nullability is read off the RESOLVED body** (`resolve_rowset`, `nullable_handles`). The body node's attribute is a construction-time snapshot: a `?` column reaches it, the body's outer-join padding (a guest's property NULL through its `~?` key) does not, and the boundary's own `_resolve` matches parents by bare address (`s.n` never finds `_s_n`). Read the snapshot and no side of the reader's FINAL is nullable on the stand-in, so the guest's NULL group joins on a plain `=` (`test_stand_in_key_pairs_the_guest`).
- `_carry_join_keys` carries a handle the node's own parent emits (`parent_output_addresses`). A ROWSET bucket gets the hidden span in `_compute_concept_sets`. Both were `ON 1=1` cross products.

### General planner bugs fixed on the way

These are not about `~`; they are worth knowing so they are not reintroduced.

- Output roots whose reach is a ROW STREAM co-source regardless of concept-graph component (`_cosource_component_groups`); two BASICs related only by a datasource FK rendered `ON 1=1`.
- A WHERE over an aggregate by a key was dropped when the key and a property were both projected. The fresh FINAL re-source now replaces the built node only when it can restate every atom. `outputs_with_parent_grain_keys` no longer offers a parent's HIDDEN outputs.
- An atom over an aggregate BY A DERIVED grain crashed (`Missing source map entry`); `_hosts_carrying_condition_grain` fixes it.
- `_concept_covers_grain`: a key covers a grain only when the WHOLE grain is that key. Otherwise a FINAL merge onto a finer row stream skipped its dedup (since #522).
- **A key the parent NULL-pads is not an FD determinant** (`check_if_group_required`, the FINAL dedup gate; both its FD-closure waiver and its "keys sit in the source grain" waiver). `select return_id, reason, pname` over `lines FULL returns FULL products` rendered with no GROUP BY: `return_id` determines `(order_id, line_no)` through `returns`' grain, so the upstream line grain looked covered, but the FD holds only where a return is PRESENT, and product `a`'s two unreturned lines came out twice (`FINAL_DEDUP`; with `lines` complete on the order, `select return_id, count(product_id)` gave three `(NULL, 1)` rows for one `(NULL, 3)`). The rule `effective_grain` already states for grain membership ("a NULL-padded key is absence, not a row identity") now holds for determinants. The determinant reaches the gate two ways: `build_fd_closure` over datasource column grains, and the model-wide FK-path `keys` a `~`-binding source at its own grain stamps on the KEY concepts it binds (`line_no.keys == {return_id}` after `returns (return_id)` binds `~line_no`; the keyspace reads those as an artifact, `from_concepts` reads them as FDs). Not done: the merge's own grain claim (`raw_pregrain`, `from_concepts` over the parents' grains) still folds through the padded key, so that FINAL's `QueryDatasource.grain` is `(return_id)` -- a uniqueness claim false on the padded rows -- listed under optimization candidates.
- **A projected row identity needs no group** (the same gate, `rows_unique_at_outputs` in `MergeNode.resolve`, `calculate_effective_parent_grain`). The rule above first cost thelook q19 (`users LEFT items FULL products LEFT orders`, the four keys projected) a GROUP BY over its outputs: the target grain folds `user.id` under `id` through the key hierarchy, then the padded `id` could not determine it back -- but `user.id` is an OUTPUT, and a projected column covers itself and determines what it determines, whatever the fold dropped it for. The merge level had the same shape twice over (`select user.id, id, product.id` grouped before the rule too): the FINAL merge's pinned grain is the union of the contributors' projection grains, which on a plain row merge is the region domains' spans alone (`(product.id, user.id)`, nobody's projection grain names the fact's `id`), and the pregrain is the same key-hierarchy fold. So the merge asks the rows directly once nullability is known: every UNFOLDED joined-grain component is projected or FD-determined by projected columns non-null on every row. Both gates needed `calculate_effective_parent_grain` to stop treating a FULL/RIGHT keyed on its right side's grain as grain-preserving: the unsold products under one NULL `(user, item)` are rows of the stream, and `select user.id, id, product.category` (the key NOT projected) must keep its group, which the understated grain had waived (`tests/engine/test_projected_row_identity.py`). A/B over the planner suites: four plans lose a redundant GROUP BY (thelook q19, adhoc03, adhoc04; TPC-H instantiated adhoc07's customer-orders CTE), rows verified; nothing else moved.
- `_satisfy_parent_projection_contract`: a parent's OWN mandatory output that is not FD at the FINAL projection grain (`quantity as q` beside `count(order_number) by item_desc`, the grain being the hidden span `item_sk`) was stripped by the projection to that grain; the `non_fd_needed` guard covered only the parent's INPUTS. Such a parent stays as built. It raised `No FINAL contributor renders ['local.q']`, and gave a `~?` guest NULL for `sum(quantity) by item_desc`.
- `select_merge_node`'s lone-scan shortcut returned the scan as the candidate without checking it applied every atom. A bare `x is null` over a column a `~` scan binds is an ABSENCE atom (`condition_routing.absence_atoms`): routed off the scan as a merge-level test and stripped from `preexisting_conditions` too, so when the search did not extend the scan nobody re-applied it and `select label where status is null` on the plain model returned every order. A lone scan (through a force-group wrapper: the plain model's `orders` binds window columns) whose remainder holds an absence atom now goes through the merge path like several parents would (`_merge_condition_routing`), and the atom is applied over it. ONLY an absence atom: a remainder is also a tautology the scan dropped (`ss.store.sk is not null`, `ALWAYS_TRUE`) or an atom over what the scan does not hold, and wrapping those grew TPC-DS q59/q66/q74 past their SQL budgets (the store scan lost its datasource inlining) before the rule was narrowed.
- `_anchor_scalars_to_dim_peel_key` read a ROOT's secondary members as a dim-peel key, and a region's span riding hidden on the solid fact scan (`region_join_keys`) re-anchored `status` to the CUSTOMER grain, where it could not carry `amount` for the WHERE and FINAL joined it to its own parent scan on the span: `select name, status where status is null or amount > 15` passed ann's delivered order (amount 10) on her other order's amount (with `customer_id` projected the span is a primary member and nothing anchored). The span is subtracted from the key. Back at the order grain, the hidden span has no `ConceptAttrs` of its own (it is not a requested concept), so the capability FD rule could not carry it through the BASIC and `select name as n2, status` cross-joined: a pointwise child of a ROOT carries the spans riding hidden on it (`_compute_concept_sets`). Carrying every region join key through every pointwise group was tried first: the two-family body's `reads:product_id` rename carried the owned `user_id` and the product extension went INNER, and the guest keyless band group carried `s.d` and lost its FINAL dedup.
- **The scan caches key the promotion.** `History._concepts_to_lookup` (the `select_history` fingerprint `_direct_source` reads) and `V4History.network_verdicts` keyed outputs + conditions only, while the search's answer reads `SpanScope.extent_free` (a promoted `~` binds fully: `network_build._candidate`, `select_merge_node`). The solid stream of a region and its domain ask for the same columns under different promotions, and the domain took the solid stream's cached scan. On two facts at ONE grain (`sales (item, ticket)` complete, `returns (~item, ~ticket, reason)`) the solid rows of the `{item, ticket}` region are the RETURNED lines, so `select item_sk, ticket where reason_class is null` (outputs exactly the spans) built its domain from `returns`: `no complete sources found`. Both keys carry the promoted set now. Every request the fix re-answers is a plan the stale cache had been answering with another group's scan.
- `ensure_content_preservation`: after `A RIGHT JOIN B` (B preserved, A padded into the accumulated stream), a join keyed off A preserved its OWN right relation, which neither keeps B's unmatched rows nor is licensed: the users dimension was RIGHT-joined into a solid fact stream (`orders RIGHT JOIN items` on a `~user_id` both bind, then users keyed off orders), and `case when state = 'CA' then qty else 0 end` took its ELSE on user 3's padding. The unit tests in `tests/generators/test_utility.py` had pinned the RIGHT.
- **Two FINAL row streams at incomparable grains related by FD** (`_compute_concept_sets`, the FINAL-sibling grain rule): `cost * amount` is keyed on what it reads, (order, product), beside `state_qty` at item grain, item -> order and item -> product. The rule exposed grain keys to a sibling only on equal or subset grains, so the two paired on the one requested key (`product_id`) and every item fanned out by its product's other orders. The coarser now exposes its grain and the finer the coarser's, ONLY for two row streams of which one is solid and the other reads a region domain: neither can fold into the other. Every wider gate was tried and moved TPC-DS: any two row streams (a grouping sibling pulled the aggregate's domain-carried grain into the ROOT), incomparable grains only (q23's customer rename beside its line values, FD-related and sharing no key, is served by the passthrough fold since both build from the same solid rows; the exposure split `quantity * list_price` into its own CTE joined back: q23/q51/q59/q66/q78 over budget), and "the shared requested keys determine neither grain" (same four). A pointwise group's capability carries a key with no concept node (`order_id`, a source grain the ROOT advertises under `amount`) through the model's FD (`build_fd_determines`), since the concept-graph FD cannot see it; the hidden-span carry above is the same blindness, handled per span.

Folded together, a HAVING predicate reaching through one of this select's own outputs met the connectivity check without them.

The step-2 retirement list was tried by deletion. These are the fallback for regions the keyspace does not model, each with its shape at the site:

- **`_keep_extension_families_together`**: the merged peel cluster is where `add_region_domain_buckets` finds a region's solid source.
- **`_add_region_domain_contributors`' rename rule**: an alias rides its source's ROOT bucket.
- **host/`host_stitch` inference in `generate_joins`**: without it a domain merge FULL-joins its readers.
- **The zero-fill guess in `dialect/base.py`**: the no-domain fallback's `coalesce(count, 0)`.
- **`_extent_free_partials` / `extent_free_carried`** (`test_unsold_item_counts_no_lines[select]`).
- **`_span_padding_matrix` / `_pads_for_different_members`**: without it two families' padding pairs NULL with NULL null-safely. `region_spans` does not yet answer "two readers of different regions".
- The `span_scope` fields go with their last reader; `Keyspace.in_play_spans` stays for pin-heal.

**Tried and reverted, with the reason:**

- Resolving a rowset key to the key it wraps: a rowset is a row source.
- An "aggregation level" rule in `_witnesses`: after heal it absorbed `users` and `orders`. The network search already picks by aggregation level.
- "No complete source: the partial ones complete each other" (shards): retracted by the owner rule above.
- Stamping every rowset boundary with its witness spans (5(c)): grew `test_rollup_label_over_union_joined_rowsets` 2546 -> 2948.
- Dropping the region from the rowset body's keyspace: it would compute `rank sk by d` over the solid items.
- **The FINAL re-source of EVERY root under the group's own extent scope** (first tried with the domain carrying only what its sources held, then 2026-09-27 for domains too). The first lost `brand` on the product extension row of `test_forked_full_column_set` (the peel case, now a domain member: region domains above); the second lost the orphan address's `state` (`test_licensed_transitive_attr_span`): a domain's FINAL re-source is where it completes a transitive `~`. Solid roots only now (region domains above).
- **Flattening the solid MergeNode into the domain merge** (parked, cosmetic). It made q22 byte-identical to its old plan, but a flat chain needs three passes that do not understand a PADDED ACCUMULATED STREAM:
  - `resolve_join_order_v2` can place an INNER after a holder's RIGHT/FULL and drop the domain's rows.
  - `ensure_content_preservation` tracks only prior ON-clause lefts.
  - Handing `held` as `extent_free_spans` strips the holder's own nullable marks.
  - `in_play - demanded` as "unlicensed" over-reaches (gcat `vehicle.class, launch_count`).

## Open items

No wrong-rows item is owed (the `OWED` list, the `array_agg` xfail, and the two items the grain twin found 2026-09-28 are cleared) and no ruling is pending (cross-dialect `array_agg` was ruled: Owner decisions). Everything left is a shape the keyspace does not model that is rows-right with a fallback standing in, or an optimization candidate: a rows-right plan doing measurably more work than a better shape that exists. An item is "cosmetic" only until a rows test exists -- that held every session of this project -- so a new item starts with one; a shape with no better shape is dropped, not listed.

**Shapes the keyspace does not model** (a failing rows test would promote one to a phase):

1. **Regions only a join of two facts witnesses** (TPC-DS q64) stand in the base region. The two-fact model's aggregates and per-fact row streams are rows-right without a region of their own (`tests/engine/test_unmodelled_regions.py`, `TWO_FACTS_CASES`), and the same-grain shape (q64's returned sale line, `TWO_FACT_JOIN_*` there) was probed 2026-09-27 (25 spellings, derived vs materialized, hand rows) and is rows-right with the base region standing in. `elect_extent_owners`' ranking branch and the rest of [What stays](#what-stays-and-why) are its fallback.
2. **Merged-`~` pin-heal** (pin-heal above): a lost optimization, never a wrong answer.
3. **A materialized rollup beside a region** gets no domain of its own (region domains above). Rows-right and guarded by the rollup-summary twin; listed so nobody reads "no domain" as "unhandled".

**Optimization candidates** (rows-right plans that do more work than a better plan would; no rows test can drive them, so each is stated as the work it wastes, with the better shape that exists):

- **A FINAL dedup over a domain merge** (`test_keys_only`, `test_join_grain`): `users LEFT JOIN items FULL JOIN products` followed by a `GROUP BY` on every key. Each side is unique on its key, so the join output is already unique and the GROUP BY is a full hash aggregate over the whole result, comparable to the join itself, and it blocks streaming; DuckDB cannot elide it through a FULL join. Optimizer pass: drop a GROUP BY with no aggregate expressions whose keys include a unique key of every joined relation. Cost grows with output rows. It is a cost of the domain keeping the FINAL's scope (region domains above).
- **A pushed atom hoisted over a preserving join it does not need** (found while fixing `extent_nullables` below, reproducible by reverting the authored veto in `_nullable_join`): when a join above a filtered CTE is typed preserving, the condition placement re-applies that CTE's already-pushed atoms at the FINAL, and the CTE has to project every column they read (q64: five extra columns, +870 chars, the predicate stated twice, and the optimizer narrows the join back to INNER afterwards anyway). Preservation toward the filtered side keeps only rows that already passed the filter, so the restatement is unnecessary exactly when the preserved side is the one carrying the atoms. Cost is per-query SQL size, not rows.
- **The forked full column set** (`test_forked_full_column_set`): to carry `brand` and `state`, a second fact-sized chain (`products LEFT items FULL users FULL orders`) is INNER-joined back to the main fact chain at FINAL on four keys with `IS NOT DISTINCT FROM`, then FULL-joined to the status stream. The fact table is joined through twice and two fact-sized streams are null-safe-joined on four keys: roughly double the join work of reading the two attributes off dimension peels. This is thelook's `order_items` shape. The better shape is the peels; the attempt that took it (every root's FINAL re-source under its own scope) lost `brand` on the product extension row, see tried and reverted. A planner fix, or an optimizer pass replacing a stream joined only to carry dimension attributes keyed on a key the other side holds with that dimension's peel.

- **A merge's grain claim folds through a padded key** (`MergeNode._resolve`, `raw_pregrain` / `calculate_joined_pregrain` through `BuildGrain.from_concepts`' key-hierarchy reduction): `lines FULL JOIN returns FULL JOIN products` declares grain `(return_id)`, since `return_id -> (order_id, line_no) -> product_id` by the FK-path keys, and that uniqueness holds on the returned rows alone. The FINAL dedup gate no longer trusts it (general planner bugs above), so it is rows-right, but every other reader of `QueryDatasource.grain` (`_join_right_preserves_cardinality` in a merge above, the optimizer's cardinality checks) reads the false claim. The honest grain is the parents' grains folded through unpadded keys only; `null_extended_sources` over the typed joins is where the padded set comes from. Cost when it bites: a skipped dedup or a mis-narrowed join above such a merge; none observed.
- **A no-op pivot lookup survives the demand typing** (`select return_id, reason, qty` still renders `LEFT OUTER JOIN orders` off `lines.order_id` after the spine rule above): the scan contributes only the key both facts already hold. Cost is one dimension scan and a hash join per query; an optimizer pass dropping a LEFT-joined relation no output reads would remove it.

**Dropped** (no better shape exists, or the shape costs nothing):

- **Flattening the solid MergeNode into the domain merge**: DuckDB and BigQuery inline CTEs, so the extra layer costs nothing at execution. Cosmetic only; the three passes that would have to learn a padded accumulated stream are listed under tried and reverted should it ever matter.
- **5(c), the rowset witness leftover** (an unsplit boundary not stamped as the region holder): stamping every boundary grew `test_rollup_label_over_union_joined_rowsets` 2546 -> 2948 with rows unchanged. Probed for rows through the oracle twin and a two-family model (`probe_rowset_twin.py`); the wrong-rows bugs in that neighbourhood were the unread region and the dim-peel anchor, both fixed. Probe `[13]` (`case when s.n_items > 1 ...` over an aggregate rowset) differs from its direct spelling by design (a rowset is a row source).
- ~~**`extent_nullables` matches raw addresses against canonical nodes**~~ FIXED: the +870 chars it cost q64 was a second bug, not the price. The key it newly marks (`ss.item.id`, canonicalizing onto the SELECT's `item_id`) is a `subset join`'s declared axis, and `_nullable_join`'s asymmetric-extent rule was the one direction inference that never consulted `facts.authored(keys)`; the condition placement then hoisted the pushed atoms over the resulting LEFT_OUTER. With the veto the pair is SQL-identical over the planner suites.

## Visual debugger (MVP, 2026-09-27)

A step-through viewer for one statement's discovery, so the keyspace can be read as a story instead of reasoned about from `[v4] built` lines: `local_scripts/plan_debugger/` (README there), recorder `trilogy/core/processing/plan_trace.py`, guards `tests/core/processing/test_plan_trace.py`.

**How it works.** The planner records each phase at its seam through `plan_trace.record` (one `active()` check when off): `_build_from_graph` (a plan scope per plan, so rowset bodies, arms and condition feeders nest; the request, the concept graph, the keyspace, the returned node), `build_group_graph` (the buckets after each grouping pass, the group graph after each topology pass, the condition placements), `plan_source` / `_network_source` (every source request with its span scope and the network search's candidates × terminals table, cover and cost), `build_strategy_node` (every built group with its atoms, parents, span scope and node tree; the FINAL contract, extent ownership and assembled tree), `get_query_datasources` (the resolved tree, where joins are typed) and `process_query` (the CTEs before and after the optimizer). `trace_query.py` runs a `.preql` (or `--text` over `--model`), adds the rendered SQL per CTE and, with `--rows`, the DuckDB result, and writes `<stem>.trace.json` plus a self-contained `<stem>.trace.html`. `TRILOGY_PLAN_TRACE=<file>` does the same from any `process_query` (a pytest case included), without the SQL step.

**What to read, per phase, for a `~` plan** (the README's "Reading a `~` plan"): the region exists with own rows and its span is output-demanded, the outputs that must be NULL on it read "absent" in the outputs × regions matrix; the `extent:<span>` bucket appears in "region domain buckets added" (the bucket diff outlines it); the domain feeds the aggregate and FINAL in the group graph; the domain's `node` step is a scan on the dimension and every other group's span scope lists the span `extent_free`; the resolved merge carries `region <span>` and its join preserves the holder; the LEFT survives the optimizer and a padded COUNT is `0-fill`. Each step's cards, graph nodes and tree nodes open in the inspector with every field the recorder kept, including the raw `GroupAttrs`, `SpanScope` and `Keyspace` values.

**Scope of the MVP, and what is not there yet.** The trace is a record, not a replay: join typing (`get_join_type` per pair, `JoinFacts`), the FINAL cover passes and the optimizer's rule-by-rule changes are visible only through their results (the resolved tree, the CTEs after optimization), where the probe tracers under `local_scripts/keyspace_ab/probes/` still print them per decision. Next candidates, in the order they would have paid off this project: a `join` phase recording each plan-time `get_join_type` call with both `SideFacts` and the rule that answered; an `optimizer` phase recording each rule application as a CTE diff; a trace diff (two traces side by side, step-aligned by plan and title) for the A/B method below; and the heal audit's two keyspaces (authored vs healed) as one step.
